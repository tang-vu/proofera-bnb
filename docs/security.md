# ProofEra security review and threat model

Updated: 2026-08-12. Scope: marketplace browser/server, live data adapters, BNB Agent Studio workers, Altana session lifecycle, PancakeSwap execution and evidence operations.

Status labels below are `implemented`, `building`, or `release gate`. Financial-risk disclosure is not treated as a substitute for a technical control.

## Assets and trust boundaries

Protected assets are user funds, admin passkeys, scoped session signers, API/RPC credentials, reviewed policies, transaction state, evidence integrity and the ProofEra brand/agent identity.

- User boundary: a browser passkey remains device-bound. ProofEra never asks for or receives its private material.
- Worker boundary: the autonomous secp256k1 signer exists only in a dedicated encrypted secret/KMS. General web runtimes, browser storage, logs and the marketplace database receive public material only.
- Network boundary: registry metadata, RPC/API responses, agent endpoints and transaction callbacks are untrusted until parsed and independently checked.
- Onchain boundary: BSC receipts and contract reads establish state; a submitted UI operation or relay response alone does not.

The repository scanner asks Git for tracked and non-ignored untracked paths; it never recursively opens ignored local state. Forbidden `.env*` files other than the root example, `.studio`, wallet directories, keystores and key/PEM filenames are reported before file access. If Git is unavailable it fails without walking the workspace. CI checkout credentials are not persisted, and license evidence is generated after verification in runner-temporary storage with commit, tool-version and SHA-256 provenance. This is defense in depth, not a substitute for a mature secret detector/SBOM before release.

Tooling must never print an entire process environment or package-manager configuration: registry tokens can be inherited from user-level config and emitted even when the repository contains no secret. Use only narrowly scoped non-secret queries, keep CI logs redacted, and rotate any credential that appears in tool output. The source scanner reports rule/path only and never matched material.

### Local BSC testnet deployer custody

A dedicated development EOA now exists for chain-97 deployment preparation at `0x997cD959798F7c925076eaeFF5855C5C2c1e5A49`. Its private key was generated with viem's secp256k1 CSPRNG path, encrypted as Web3 Secret Storage v3 with scrypt (`N=131072`, `r=8`, `p=1`) and AES-128-CTR, and stored outside the repository. The independent 48-byte random keystore password is wrapped with Windows DPAPI `CurrentUser`; the local directory has inheritance disabled and one effective allow rule for the current Windows SID. A second process independently unwrapped the password, verified the keystore MAC, recovered the same address and recovered an offline EIP-191 signature. Only the public record is retained in [`evidence/development/bsc-testnet-deployer-wallet-2026-08-12.json`](../evidence/development/bsc-testnet-deployer-wallet-2026-08-12.json).

This is a temporary testnet custody boundary, not an Altana admin/session wallet, user funding wallet, production KMS, hardware wallet or mainnet authority. An EVM key is not chain-bound, so every future signer must independently require chain ID 97. DPAPI does not protect against malicious code running as the same Windows user or a sufficiently privileged administrator, and the blob is not a portable backup. No RPC read, funding, transaction or deployment was performed; balance and history remain unknown. Fund it only with the minimum faucet tBNB needed after the exact unsigned plan, fee cap and destination are reviewed, and never reuse it on mainnet.

### Operational incident: exposed npm registry credential

On 2026-08-11, a local package-manager configuration diagnostic emitted an npm authentication token into tool output. The credential value is deliberately not reproduced or retained in repository documentation. It must be treated as compromised even though source-boundary scans do not find a repository copy. Required account-owner actions are to revoke/rotate it, review npm access/publication history for unexpected activity, invalidate any duplicated use, and confirm completion before public release. Replacement credentials must stay in the owning credential store and must not be supplied to ProofEra code or logs. Repository work now prohibits environment and package-manager configuration dumps; this process control does not prove that account-side rotation occurred.

## Session-key protocol

Required bootstrap record fields are user/session ID, Altana wallet, session public key/address, canonical policy hash, nonce, issued/expiry times and state. The worker creates the key before the grant, stores it encrypted, and deletes orphaned secrets after a short TTL. Only its reviewed public descriptor crosses the API boundary.

The pure worker lifecycle implements that boundary with an opaque secret handle, domain-separated binding hashes, injected clock/ID/nonce sources, a non-retryable unknown state, exact authority verification, replay/freshness checks, and TTL-gated idempotent cleanup. The marketplace browser projection omits the handle and provider response. The grant adapter additionally requires the exact persisted transition, an explicit configured RP ID matching the production WebAuthn credential, a curve-valid P-256 public key, and an atomic one-shot claim before SDK invocation. Its sanitized response contains no signer, credential, secret handle, SDK function, raw error, or `callsId`. The append-only PostgreSQL 17 claim ledger binds bootstrap/idempotency/bootstrap-hash/submission-hash independently and never reclaims identifiers. Its canonical migration, independent catalog/ACL/namespace/role-setting verifier, same-pool application gateway, exact deployment UUID check, SQL result limits, timeouts, no retry, acknowledged commit/rollback, and ambiguous-outcome sanitization pass 68 focused and 18 real PostgreSQL tests. A stalled verifier client is destroyed, and a post-timeout operation cannot continue to INSERT or COMMIT. The package exports only the server composition; raw SQL/verifier/transaction internals stay private. This is implementation evidence, not production durability: no database, KMS/secrets provider, authenticated/origin-checked endpoint, or log-redaction proof is deployed.

The tested permission-preview model and server-renderable component show the wallet, BSC testnet chain 97, target/function rows, raw-unit token caps with decimals, expiry, fee token, emergency behavior and revoke consequence, labelled by enforcement owner. They are not yet wired into the `/lp-activate` route or a wallet ceremony, so the current browser journey must not claim that a grant was previewed.

After a successful SDK return, and after every ambiguous return, the worker independently reads wallet keys/Keystore registration. A resolved SDK grant advances only to `authority_pending`. The worker enables execution only if wallet, curve/public key, byte-exact permissions, expiry and policy hash match. Unknown or mismatched authority disables action. Altana SDK 0.7.0's grant call does not expose `callsId`; a pending exception cannot be blindly reconciled through that ID.

Revocation requires the admin passkey. Requested/pending/unknown revocation retains an active warning. Only fresh invalid-authority reads make it revoked. Emergency documentation must include direct explorer/contract fallback steps after the exact SDK path is proven.

## PancakeSwap execution policy

Milestone 1 uses direct reviewed V3 Position Manager functions only. A manifest entry binds chain ID, contract address, deployed code hash or verified implementation identity, exact signature and selector, allowed token pair and semantic validator version. The reviewed-deployment schema separately derives `reviewId` from the canonical complete source/review metadata, fee/tick spacing, token decimals and runtime-identity manifest; any mutation breaks the content address. This prevents an approved snapshot from being silently altered, but it does not establish source verification, non-proxy status, implementation/admin immutability, token behavior or release approval.

The pure calldata gate currently permits only canonical, direct `mint`, `increaseLiquidity`, `decreaseLiquidity` and `collect` calls to the official BSC testnet Position Manager. It rejects non-canonical encodings, trailing data, nested dispatch, unknown selectors and any native-BNB value. It binds each decoded argument to a separately validated server plan without converting financial values through JavaScript numbers. A ready result is not authorization to submit: the live runtime must still rebuild the plan from current evidence, verify code identity and authority, simulate, and rerun the gate immediately before signing.

Runtime-code identity has its own fail-closed reader. It accepts only a previously bound block number/hash/timestamp, verifies that block by hash, and issues EIP-1898 `eth_getCode` reads with `requireCanonical: true`. Provider rejection is unavailable and never falls back to `latest` or a block number. The reader returns only byte lengths and Keccak runtime hashes; a match does not prove verified source, proxy implementation, upgrade safety, or behavior.

Position authority has an independent fail-closed reader. It binds the commit-pinned official chain-specific Position Manager, NFT ID, intended controller, block number/hash/timestamp, and server clock. The freshness policy and credential-free provider identity belong to trusted reader configuration and cannot be widened by request data. `ownerOf`, `getApproved`, and `isApprovedForAll` are canonical 32-byte ABI reads at the exact EIP-1898 block hash. Owner, token-level approval, and operator approval are reported separately; unauthorized is a valid observed state, while a revert, malformed word, chain mismatch, stale/future block, invalid reader configuration, or provider failure remains unavailable. The read grants no authority and must be repeated immediately before submission.

Manager constructor relations and token decimals have a separate fail-closed exact-hash reader. It verifies `factory()` and `deployer()` against the commit-pinned deployment, records nonzero `WETH9()`, and reads canonical `uint8` decimals from the exact token order supplied by the block-pinned pool snapshot. Freshness and provider provenance are server configuration. Sequential exact-block success establishes only those returned values; it does not establish token economics, transfer behavior, runtime-code identity, source verification, proxy safety, or permission to execute.

Immediately before each submission ProofEra rechecks:

- BSC testnet/mainnet, contract address/code identity and selector;
- wallet recipient, LP token ID ownership and expected token pair;
- tick spacing, ordered bounds and maximum range change;
- liquidity/amount bounds, token decimals and aggregate spend cap;
- quote observation time, maximum age and TTL, slippage/minimum amounts and deadline;
- execution count/rate, policy expiry and current session authority;
- simulation outcome and decoded calldata equality with the previewed policy hash.

Altana enforces target/selector, spend and expiry, not these arguments. If a judge-facing claim requires argument enforcement against a compromised worker, ProofEra will add and audit a narrow guard contract or narrow the claim.

## Data and web security

- External responses are parsed with strict/bounded schemas and bounded time/body limits. Raw payloads stay server/evidence-side.
- User-controlled query values are finite enums; no query/cookie may select fixture publication or execution targets.
- Names/descriptions render as text. External links use known HTTPS origins. Future endpoint fetches require SSRF controls and never forward credentials across redirects.
- Current headers include CSP framing/base/object restrictions, HSTS, nosniff, referrer, opener/resource and permissions policies. CSP allowances must be tightened alongside the final Altana browser endpoints.
- Sensitive mutations require authenticated same-origin requests, CSRF/origin checks, rate limits, replay nonce and audit events.
- Logs exclude authorization headers, API keys, cookies, WebAuthn payloads that reveal unnecessary material, private/session keys and raw signed calldata where it creates risk.

## Operational response

If a session or agent is suspected compromised: disable new executions, mark the marketplace agent suspended, request admin revoke, observe onchain invalidity, remove endpoint discovery, preserve non-secret audit evidence, rotate worker/API credentials, investigate affected policy hashes and publish an incident note. Never claim funds are safe until authority and balances are read.

## Required adversarial verification

- Public-descriptor grant on exact SDK 0.7.0; pending-to-late-confirm without retry; orphan cleanup; byte-exact authority comparison.
- Rejected/pending/failed/confirmed execute and revoke; reload, crash, double-click and two-tab idempotency; revoked/expired key cannot execute.
- Wrong contract/selector/code hash, dispatcher overloads, malicious recipient/token ID/tokens/ticks/minimums/deadline, duplicate caps and decimals mismatch.
- 8004scan empty/429/502/timeout/schema drift/huge response; stale last-good; malicious metadata/URL/SVG/redirect and production fixture-leak.
- Final-host virtual WebAuthn E2E plus a manual real-device create/recover/grant/revoke ceremony.

## Open release gates

- Durable HTTPS origin and exact RP ID are not configured. Production rejects IP, loopback, special-use, and public-suffix-only names; a real-browser ceremony on the final host remains required.
- No real Altana wallet/session/grant/execute/revoke receipt exists yet; the passing grant tests inject a signer-shaped object and never invoke WebAuthn or a network.
- The Altana LP handoff now has a concrete server-only PostgreSQL `consumeOrRead` implementation. Its versioned append-only migration, externally pinned PostgreSQL 17 catalog/ACL/rule digest, nominal administrator-verification capability, least-privilege application pool, bounded transaction outcomes and 10 real-PostgreSQL 17.9 cases pass. Activation rejects structural callback lookalikes, joins policy/attestation block number+hash+timestamp, uses monotonic clocks, and discards nested ready state if final receipt or target freshness fails. No production database is provisioned, so persisted bootstrap, live authority and production replay protection remain unavailable.
- Pancake intent and direct-calldata validation are implemented. Write-target attestation v2 isolates four direct Position Manager selectors and explicitly denies the manager's reachable self-`DELEGATECALL` multicall dispatchers. The earlier address-case write-scope mismatch was caught before authorization; the local raw-byte artifacts were deterministically regenerated against the canonical lowercase-manager hash and now pass a drift regression. They remain non-authorizing. A server-only intake rejects the local package and emits only a nested assessment after exact public bytes, fresh no-redirect retrieval records, allowlisted identities, and a separately provisioned review ID. A bounded exact-lineage search rejected all 14 reviewed WBNB pools for unsafe/unknown token controls, inadequate oracle history or liquidity quality; its documented historical interval is not covered. Canonical WBNB now passes an exact source/creation/runtime/control review, closing only that token-component gate. PTA passes an isolated fixed-supply test suite but is undeployed, non-economic and not pool evidence. Its offline pool-preparation tool emits only exact zero-value initializer calldata and an explicitly blocked review plan: it omits approvals, liquidity, signatures, transaction envelope and pool prediction, and discloses the initializer race. Actual selector publication/retrieval, an approved PTA deployment or other eligible token, an eligible deployed pool, live server-plan construction, current identity checks, simulation, authority binding and a testnet receipt remain release gates.
- Durable Agent Studio hosting and four live BSC agents are not yet deployed.
- The published Altana SDK 0.7.0 artifact is GPL-3.0-or-later; distribution obligations and conflicting repository metadata require resolution.
- CI actions are SHA-pinned and source-boundary secret, digest-pinned real-PostgreSQL, and production-license inventory gates exist; a standard SBOM and Altana license resolution remain release gates.
- The npm-account owner must confirm revocation/rotation of the credential exposed in local tool output and review account activity; repository scans cannot close this account-side incident.
