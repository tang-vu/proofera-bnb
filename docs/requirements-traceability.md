### PTA/WBNB TTY transport evidence boundary

The historical v1 attempt was bound to exact release commit `1a89ddae5e1f575b39dda6134d3ccedaddda0adf`, tree `b28a12f78861183ece5ff1c3fce36c0abf094239`, runtime-manifest SHA-256 `0xd5212c7563d5d3e3b10d461b5dedcc1552766262c1c87a7057b4dc2876ed0ce0`, and canonical policy digest `0x9357b560a91b1c41ef8ef84ea39001c206f50fc9839a55102f7916152160a189`; both exact-release audits were `GO`. The `8,670`-byte policy had `11,560` unpadded-base64url characters, making its complete single-line frame `11,713` characters. Windows Console truncated the line and policy admission rejected it fail-closed. The policy was not admitted and ACT-03 owner confirmation was not reached. At most, read-only recovery/journal inspection occurred; the attempt made no fresh RPC call, accessed no custody artifact, did not invoke DPAPI or unlock custody, and created no signature, new transaction hash, send, receipt, pool, or liquidity. After the source changed, those v1 values became historical evidence only, not a current ACT-03/SEC-01/SEC-02/CAKE-02 release authority.

The current transport requirement is a strict nonce-bound ASCII v2 `BEGIN`/ordered `CHUNK`/`END` state machine with one absolute five-minute deadline. Every line binds its line index, exact chunk count, policy byte length, and lowercase raw policy-byte SHA-256; each chunk also binds its chunk index. Only exact LF or CRLF is accepted. The hard content-line cap is `4,096` bytes, while maximum valid worst-case construction is exactly `2,618` bytes and is conservatively tested at `<= 2,700`. Total transport is bounded to `102,400` bytes, policy to `1..65,536` bytes, and each non-final payload to exactly `2,304` canonical unpadded-base64url characters; the derived chunk count is at most `38`. The historical `11,560`-character policy becomes six chunks/eight total v2 lines but remains non-authorizing. A one-off local Windows Console observation motivated these conservative constants, but its harness and result are not retained and it is not reproducible repository evidence. Repository unit tests establish only the transport arithmetic and parser behavior. V1, truncation, bad encoding/length/hash, duplicate/missing/reordered lines, control/blank input, and trailing or buffered data reject before policy admission, fresh RPC, custody access, or owner authority. Those unit tests do not prove an empty OS input queue or protection from preload/malicious same-user code. A current v2 commit/tree/manifest, exact audits, matching policy, owner confirmation, and explorer-verifiable receipt remain separate requirements.

The next exact v2 exercise bound release commit `36f6e5e7fa8b4b5ccf255a6210afa2d25c25afa5`, tree `54ed5c2a8f754e79080528a2ce25669a6532a66b`, runtime-manifest SHA-256 `0x25e5aedb6d73e6fff416803ce9d42737d9124e525e0b81bf906321f4d06258d4`, and admitted canonical policy digest `0xd1a33479a607d744a51ff8d6d3df8772f41ec2f1363911d2655f926c754c3b38`. Signing and submission journal recovery probes were absent; fresh read-only dual-official-RPC preflight succeeded and the exact owner challenge was displayed. No exact owner confirmation was accepted. Subsequent attempts failed closed with `POLICY_FRAME_INVALID`, `CEREMONY_IO_FAILED`, and `OWNER_CONFIRMATION_INVALID`; they accessed no custody artifact, invoked no DPAPI/unlock, and produced no signature, new transaction hash, send/broadcast, receipt, pool, or liquidity. This was a one-off local terminal observation; its raw output and harness were not retained, so it is not reproducible repository evidence or a gate. The negative custody/sign/send statements reflect the observed fail-closed result plus code ordering rather than a retained artifact. A later timing-source change made this triplet/policy historical and non-authorizing.

The current-source timing trace separates an exact `300`-second envelope, at most `240` seconds for owner entry, an exact `45`-second execution authority, and `30`-second post-claim freshness. The strict owner deadline is `min(challengeIssuedAt + 240 seconds, envelopeExpiresAt - 45 seconds)`. V4 owner bytes bind `challengeIssuedAt`, `confirmationNotAfter`, the lifetime, and the deterministic derivation rule; only after exact byte match does the internal clock capture actual `confirmedAt`, and the `WeakMap`-branded v4 command binds actual `executionExpiresAt = confirmedAt + 45 seconds`. A refreshed post-claim timestamp must be `>= confirmedAt` while keeping that expiry. The TTY-v2 transport constants remain unchanged. The `00f21c4` request generator, test, and retained artifact stay pinned to the historical 45-second envelope and are not producer/evidence for this timing revision.

## Evidence update rule

A row moves to `verified` only when the linked test/receipt/output exists and has been checked. UI code, a screenshot of a disabled control, or a planned transaction is not onchain evidence.
