Verified 2026-08-11:

- Current documented and npm release is exact version `@altananetwork/sdk@0.7.0` with `viem`; it is pre-1.0 and must be exact-pinned. The browser and server share the TypeScript SDK.
- Licensing check: the installed 0.7.0 package manifest declares `GPL-3.0-or-later` and ships the GPLv3 license. This conflicts with the repository metadata previously observed as Apache-2.0 and with ProofEra's current MIT root manifest. Treat the published package as GPL unless Altana clarifies otherwise; complete a license/SBOM review before any public distribution or official-adoption claim.
- Create clients with `createClient({ chains: [BNB_TESTNET] })`. Browser admins can use `createPasskeyWallet`/`recoverFromPasskey`; server agents use a separately secured signer.
- `grantSession` accepts wallet, admin signer, explicit `permissions.calls`, `permissions.spend`, Unix expiry, optional session signer, `register` (default true), fee token, and chain ID. Omitting calls is unrestricted, so ProofEra always supplies calls and spend.
- Call permissions can bind both `to` and a function `signature` with AND semantics. ProofEra uses both wherever feasible and rejects broad router access—especially generic `multicall`—unless nested calldata is decoded and policy-validated.
- A registered grant atomically writes the session key to Keystore and authorizes the permissions hash. `execute` accepts either admin wallet+signer or a session. `revokeSession` atomically removes Keystore/account authority and is monotonic.
- `execute`/`revokeSession` return `{ callsId, status, transactionHash? }`; `FAILED` and `PENDING` do not throw. ProofEra must retain `callsId`, reconcile pending state before retry, and prevent double execution.
- Important SDK 0.7.0 grant limitation, confirmed against the installed package on 2026-08-11: `grantSession` waits internally, then throws for `FAILED` or `PENDING` and discards the submitted `callsId`. A relay timeout is therefore an **unknown outcome**, not a safe failure. ProofEra must never blind-retry a grant; it must hold the pre-generated session descriptor stable, probe the account/Keystore authority, and keep activation non-executable until the exact authority is observed or Altana exposes a calls-ID-bearing/no-wait API. This limitation is tracked as an upstream question.
- BSC testnet config: chain `97`, RPC `https://bsc-testnet-rpc.publicnode.com`, relay `https://testnet-relay.altana.network`, Altana explorer `https://testnet.altana.network`.
- Testnet KeyStore `0x6b8361C29d05D498b1a12B54A37310f94171E94A`; KeyStoreController `0xb530D1971f5453F3359518343F05D0AedFfF7e12`.
- Mainnet KeyStore `0x6572427ED530BadcF7375Cf9A4709D8d2b0E7E0a`; KeyStoreController `0x0834Ee2C9BdC3E3efF0a2dC34393D4B0e546A555`.
- Spend limits use raw units. BSC USDT/USDC use 18 decimals according to Altana docs; decimals will still be read and checked onchain before activation.
- `hireErc8183Agent`, `getErc8183Job`, deliverable helpers, settle/dispute/refund calls, and exported `ERC8183_ADDRESSES` exist for BSC 56/97. ERC-8183 is milestone 4, after the core session path is proven.
- Passkey recovery requires the same RP ID and an initial onchain transaction. Test/deploy hostnames therefore affect durable recovery and must be planned before evidence collection.
- WebAuthn Level 3 requires an RP ID to be the origin's effective domain or one of its registrable-domain suffixes; a public suffix such as `com` is invalid, direct IP identification is not a production RP-ID path, and HTTP is allowed only for `localhost`. ProofEra therefore validates the configured production hostname with exact-pinned `tldts@7.4.9` and its lockfile-pinned Public Suffix List parser, rejects IP/special-use/public-suffix-only hosts, and continues to require an exact origin-host/RP-ID match. Sources: [W3C WebAuthn Level 3, RP ID](https://www.w3.org/TR/webauthn-3/#rp-id) and [tldts repository](https://github.com/remusao/tldts), checked 2026-08-11.
- The SDK does not currently accept an injected MetaMask/Rabby signer as the Altana admin. A conventional wallet is funding/identity UX; the user’s Altana admin is a browser passkey. The autonomous session signer must be created and stored outside the browser in an encrypted worker secret, while only its public descriptor crosses into the grant UI. Static inspection confirms the secp256k1 grant path consumes the session signer’s public key/address but signs the grant with the admin. The strict public-only session `Signer` shim and browser grant adapter now pass exact-0.7.0 shape tests. The latter requires a production WebAuthn signer with a curve-valid P-256 public key and explicit matching RP ID, but the tests inject that shape and do not constitute a real ceremony.
- Pure integration boundaries now validate a curve-correct public-only session descriptor, serialize exact BSC-testnet grant permissions, compare authority byte-for-byte, and model execute/revoke operation state. Execute and revoke retain valid SDK `callsId` values, reject duplicate submission/retry, and never infer a transaction hash. A relay-confirmed revoke remains pending until a fresh, exactly bound authority read proves the key absent. These are 0.7.0-shape contract tests, not proof that a real passkey ceremony or transaction succeeded.
- The worker bootstrap state machine binds user, wallet, policy hash, exact permissions, nonce, short TTL, session expiry, public descriptor, and an opaque provider handle. Its browser projection never contains that handle or provider material; ambiguous secret creation/grants are non-retryable; only a fresh, exactly bound authority probe enables execution; and orphan cleanup is handle-only after TTL. Seventeen focused bootstrap tests cover tampering, replay, two-tab idempotency, stale/future probes, expiry, and sanitized cleanup failure. Sixteen additional grant tests cover exact transition/request binding, one-shot claims, P-256/RP-ID rejection, duplicate tabs, SDK outcomes, sanitization, and settlement. The one-shot ledger is now a canonical PostgreSQL 17 boundary: migration artifact SHA-256 `fced0c471135a969a726eb1e2233c9b18976c0a2d66377fa40a9d52a552d17cb`, independently authored semantic-contract SHA-256 `fc81399172bf962fe4d0b017d58846a3651ca5ccd850004e20d280ebdad9639a`, exact database/role/catalog/ACL/namespace/role-setting checks, module-owned same-pool gateway, deployment-UUID binding, fixed bounded SQL, acknowledged commit/rollback, and fail-closed unknown outcomes. Sixty-eight focused and 18 real PostgreSQL cases pass, including 16-way exact replay, disconnect ambiguity, catalog/namespace/role-setting mutations, restricted-ACL restoration, stalled-verifier destruction, and prevention of SQL continuation after timeout. Only the server composition is package-exported. Its readiness still truthfully reports no deployed database; the provider/KMS adapter and real ceremony remain deployment work.
- The LP activation context is now schema v3. It embeds the complete strict user intent and complete block-pinned quote, then derives domain-separated context and quote IDs over those payloads plus server-held nonces. The reviewed-deployment `reviewId` is independently content-addressed over the complete canonical manifest and rejects any field mismatch. These bindings prevent silent input substitution; they do not prove source verification, non-proxy status, upgrade safety, token behavior, or release approval.

### PostgreSQL activation replay boundary

Checked 2026-08-11 against PostgreSQL 17's official [Read Committed isolation](https://www.postgresql.org/docs/17/transaction-iso.html), [privilege model](https://www.postgresql.org/docs/17/ddl-priv.html), and [system catalogs](https://www.postgresql.org/docs/17/catalogs.html). Read Committed gives each statement a fresh committed snapshot; this is why the conflict path performs a new plain `SELECT` after a unique-insert race rather than using `FOR SHARE`, which would also require an unwanted update privilege. The application role has only schema `USAGE` plus reservation-table `SELECT`/`INSERT`; owner, role membership, public/third-party grants, default ACLs, column ACLs, rewrite rules, policies, triggers, indexes, defaults, constraints and function ACLs are included in the externally pinned catalog proof.

The versioned migration source SHA-256 is `922492ba66bbac7fb389a16845ebaa3144f875d3d5beb2417124f3e8188312ba`; the reviewed OID-free PostgreSQL 17 catalog SHA-256 is `9da7596295ced6586488fde39d0e3cfb4f90feb1b989a2dc4ce7a08c7276de90`. A module-private nominal capability prevents copied or serialized "ready" objects from enabling the runtime pool. Ten real PostgreSQL 17.9 cases applied the unmodified migration, ran the administrator verifier, connected as the direct LOGIN application role, exercised concurrency/replay/append-only behavior, and detected weakened constraints, rogue grants and rewrite rules. CI uses the official `postgres:17.9-bookworm` image pinned to index digest `sha256:47f917f7409eacd22fc5dfb1dee634e1b55cf0c01d1a7eb701be2227a03e0641`; see the [Docker Hub artifact record](https://hub.docker.com/layers/library/postgres/17.9-bookworm/images/sha256-c1f8a8e5a6c04a99752edbb4c7eda8eacb1e4c439d03b8fd9a29f746b33cfcd5). This proves the implementation, not a production deployment.

## Architecture decisions made from research

1. Use a pnpm TypeScript monorepo: Next.js web app, pure domain package, and server-only integrations package. Add persistence only for a concrete invariant: PostgreSQL now backs atomic activation replay reservations, while a broader evidence index still requires measured retention/load need.
2. Use an evidence envelope for every metric: raw value/null, unit, source, observed time, ingestion time, methodology, freshness, and environment.
3. Ingest broad ERC-8004 identity data but publish “verified” and activation only for curated records with independently checked endpoints and evidence.
4. Begin with an LP-range vertical slice, then reuse the same passport, permission, transaction, and Proof Stream primitives for the other three categories.
5. Default execution to BSC testnet and Altana `BNB_TESTNET`. Treat grant, execution, and revoke as explicit state machines with receipts and reconciliation.
6. Keep the PostgreSQL reservation ledger isolated, append-only and least-privilege; do not turn it into a general indexer without measured retention/load need. Defer a calldata guard contract only while judge-facing claims are limited to the exact guarantees Altana and the runtime actually enforce; add a small audited guard if argument guarantees must survive a compromised worker.
7. Keep current Node Studio reference-agent workspaces separate from the pnpm marketplace. The 48-hour BNB platform is development-only; judged uptime uses durable hosting.
8. Use Venus for the health category and Lista as a read-only mainnet yield source initially; neither expands milestone-1 write scope.
